# 보안 경계와 운영 주의사항

이 서버는 단일 운영자용 로컬 브리지다. 사용자의 소스와 브라우저에 접근하는 도구를 ChatGPT에 제공하므로, 터널 연결 자체와 실행 권한의 안전성은 따로 평가해야 한다. 여러 신뢰 수준의 사용자가 하나의 상태 폴더와 커넥터를 공유하는 서비스로 배포하지 않는다.

## 서로 다른 세 가지 권한 영역

파일 도구는 지정한 소스 폴더에서만 동작한다. 경로 이탈, 민감한 경로 이름, 심볼릭 링크와 하드링크, 특수 파일을 차단한다. 개인용 기본값에서 쓰기는 활성화되며 현재 해시와 일치하는 파일에만 적용한다. `CHAT2LOCAL_ALLOW_WRITE=0`으로 끌 수 있다. 그러나 이름 기반 차단은 모든 비밀값을 탐지하는 분류기가 아니다. `my-project.txt`에 비밀번호가 들어 있으면 일반 파일 읽기로 반환될 수 있다. 처음부터 자격 증명을 제거한 소스 폴더를 선택한다.

코드 모드 워커는 **운영체제 샌드박스** 안에서 생성된 JavaScript를 실행한다. 호스트 JS eval, `node:vm`, `worker_threads`를 안전 경계로 쓰지 않으며, 샌드박스가 없으면 실행을 **거부**한다. 백엔드 선택은 Codex의 `get_platform_sandbox()`와 같은 모델이다. 즉 플랫폼 네이티브 샌드박스를 우선하고 컨테이너를 유일한 선택지로 두지 않는다.

**macOS — Seatbelt (기본값).** `/usr/bin/sandbox-exec`에 절대 경로로만 접근한다. PATH 탐색을 하지 않으므로 공격자가 심어둔 `sandbox-exec`이 대신 실행될 수 없고, 이 경로가 이미 변조되었다면 공격자는 이미 root 권한을 가진 것이다. 정책은 `(deny default)`로 시작해 필요한 것만 열거하며, 프로필의 기반은 Codex `codex-rs/sandboxing`이 참조하는 Chromium macOS 샌드박스 정책과 같다. 경로는 정책 텍스트에 문자열로 끼워 넣지 않고 `-D` 파라미터로 전달하므로, 정책 문법을 포함한 디렉터리 이름이 프로필을 바꿀 수 없다. 네트워크는 허용 규칙을 **한 줄도 추가하지 않는 방식**으로 차단한다. syslog 유닉스 소켓도 열지 않는다.

**그 밖의 플랫폼 — Docker.** 컨테이너에는 호스트 디렉터리와 Docker 소켓을 마운트하지 않고, 네트워크·Linux capabilities·root 실행을 비활성화하며 메모리·프로세스 수·시간·출력을 제한한다.

두 백엔드 모두에서 파일 도구 호출은 브로커가 세션과 입력 스키마 및 읽기/쓰기 구분을 다시 확인한다. 코드 모드 워커에는 프로젝트 폴더 읽기 권한을 주지 않는다. 모든 파일 접근이 브로커 RPC를 경유하므로 워커가 직접 소스를 열 이유가 없다.

### 두 백엔드의 경계는 같지 않다

동등하다고 주장하지 않는다. 다음 차이를 알고 선택한다.

- **자원 상한이 약하고, 일부는 아예 없다.** Seatbelt는 권한을 통제하지 자원 소비를 통제하지 않는다. Docker의 `--memory` / `--pids-limit`에 대응하는 기능이 없다. 적용되는 것은 파일 디스크립터 수, 생성 파일 크기, 코어 덤프 금지뿐이다. **프로세스 수 제한(`ulimit -u`)은 의도적으로 걸지 않는다.** macOS에서 이 값은 프로세스 트리가 아니라 **해당 UID 전체**를 세므로, 작은 값은 일반 데스크톱 세션에서 즉시 `fork: Resource temporarily unavailable`로 실패하고 안전한 큰 값은 아무것도 제한하지 못한다. `--pids-limit`의 대응물이 아니며, 그런 척하는 편이 빈틈을 인정하는 것보다 나쁘다. `ulimit -v`는 macOS/arm64에서 동작하지 않는다. 폭주 작업에 대한 실효 제한은 실행 시간 제한과 출력량 제한이다.
- **호스트 도구가 보인다.** Seatbelt 워커는 별도 이미지가 아니라 운영자 본인 사용자로 실행되며 `/usr/bin` 등 시스템 경로를 읽을 수 있다. 컨테이너처럼 "이미지에 없는 도구는 존재하지 않는" 상태가 아니다. 다만 프로젝트·홈 디렉터리·인증 파일에는 접근 권한이 없다.
- **커널 자체는 방어 대상이 아니다.** Seatbelt와 Docker 모두 해당 커널 기능의 취약점까지 방어한다고 보장하지 않는다.

Aside는 이 컨테이너 경계 밖이다. 개인용 기본값으로 활성화된 `aside_native`는 운영자의 호스트 CLI와 브라우저 권한을 사용하며, CLI가 제공하는 파일·네트워크·로그인 기능에 접근할 수 있다. 모든 옵션을 그대로 전달하는 기능과 최소 권한 격리를 동시에 보장한다고 주장하지 않는다. 이 개인용 기본값으로 서버를 실행하는 운영자는 그 권한을 위임하는 것이다. `CHAT2LOCAL_ALLOW_ASIDE=0`으로 끌 수 있고, 서브에이전트 권한은 기본 `full-access`에서 `CHAT2LOCAL_ASIDE_PERMISSION=guard`로 제한할 수 있다. 안전성이 더 중요한 환경에서는 이 기능을 끄거나 별도의 전용 사용자/VM 안에서 런타임과 Aside를 함께 운영한다.

## 인증과 호스트 보호

서버는 코드·명령·환경 변수 전체를 도구 호출 로그로 기록하지 않는다. Docker/Aside 자식 프로세스에 환경 전체를 상속하지 않아 OpenAI 터널 키나 NODE_OPTIONS가 따라가지 않도록 한다. 다만 Aside는 자신의 정상적인 사용자 로그인 저장소에 접근할 수 있고, 도구 결과나 작업 stdout에는 프로그램이 출력한 비밀값이 있을 수 있다. 도구 결과가 ChatGPT로 전송된다는 점은 변하지 않는다.

상태 폴더는 프로젝트 밖에 두고 0700, 기록 파일은 0600으로 만든다. 원본 코드와 작업 결과 일부를 포함할 수 있으므로 상태 폴더도 민감하게 취급한다. 소스 폴더와 상태 폴더를 서로 중첩할 수 없다. 같은 상태 폴더에 여러 런타임이 쓰는 것을 잠금 파일로 막고, 종료된 프로세스의 잠금만 자동 복구한다. PID 재사용이나 잘못된 잠금 파일은 운영자가 확인해야 한다.

개인 Mac·도그푸딩 호스트에서 install/build/typecheck/test를 실행하거나 실제 인증 파일·브라우저 프로필·키체인을 읽어서 검증하지 않는다. 개발용 검증은 격리된 작업 환경 또는 이 저장소의 hosted CI에서만 수행한다. 다른 Git worktree와 HOME 변수 변경만으로 격리를 달성했다고 보지 않는다.

## 알려진 경계

Docker·Seatbelt와 호스트 커널 자체의 취약점까지 방어한다고 보장하지 않는다. 운영자가 지정한 Docker 데몬·실행 파일·이미지는 신뢰 기반이다. 이미지는 미리 검토하고 digest를 고정하며, 불필요한 호스트 서비스를 컨테이너에 연결하지 않는다. Seatbelt 경로에서는 `/usr/bin/sandbox-exec`과 운영자가 지정한 인터프리터 경로가 같은 신뢰 기반에 해당한다.

같은 OS 사용자 권한을 가진 악성 로컬 프로세스가 경로를 실시간 교체하는 경쟁 공격은 완전히 방어하지 않는다. 경로 검사와 최종 파일 O_NOFOLLOW, 파일 해시 재확인은 일반적인 경로 이탈·실수·동시 편집을 줄이지만 OS 권한 분리의 대체재가 아니다. 신뢰할 수 없는 로컬 사용자가 있으면 전용 OS 계정 또는 VM이 필요하다.

쓰기 배치는 트랜잭션이 아니며 취소는 rollback이 아니다. 외부 작업을 포함한 exactly-once 실행도 보장하지 않는다. 작업 ID와 입력 지문은 같은 저널에서 중복 제출을 막고, 실패한 작업을 자동으로 다시 수행하지 않도록 하는 장치다.

MCP의 readOnlyHint/destructiveHint는 클라이언트의 판단에 도움을 주는 표시일 뿐 실제 권한 검사를 대신하지 않는다. 외부 행동을 포함할 수 있는 `code_mode`는 읽기 전용으로 표시하지 않는다. 배치 실행은 내부 도구 호출 하나마다 ChatGPT 승인 화면을 새로 띄우는 구현이 아니다. 외부 배치 호출 전체의 내용과 권한을 사용자에게 설명하고 승인받아야 한다.

> 출처: [MCP tools — annotations와 입력 검증](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

Seatbelt 백엔드에는 정리할 데몬 측 상태가 없다. 작업 디렉터리만 삭제하면 끝이며 남는 컨테이너도 없다. 반대로 강제 종료·커널 종료·Docker 데몬 장애 뒤에는 `chat2local-...` 컨테이너가 남을 수 있다. 정상 취소는 프로세스 그룹 종료와 컨테이너 제거를 시도하고, 정리를 확인하지 못하면 성공이라고 보고하지 않는다. 강제 종료 후에는 운영자가 실제 컨테이너와 파일 변경을 확인한다. 재시작이 작업 프로세스를 자동 복원하거나 모든 로그를 복구하지는 않는다.
